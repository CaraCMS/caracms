# CaraCMS on a Starlight site

**CaraCMS owns the pages; Starlight owns the chrome.** Every docs page is a CaraCMS page
(JSON in `content/pages/`, edited at `/admin` on the page itself), served by caracms's
catch-all route. The site's page component draws it inside Starlight's `<StarlightPage>`, so
it looks and navigates like any Starlight site. Starlight's own `docs` collection stays
empty.

| Thing | Who provides it |
|---|---|
| `<html>`, head, header, theme select, search, layout, table of contents, prev/next, 404 | **Starlight**, through `<StarlightPage>`. It writes the whole document, so caracms's `<Head>` and `<Fonts>` aren't used |
| Pages, their order and nesting, editing, publishing, media | **CaraCMS** |
| The sidebar | **The kit**, from caracms's page tree, passed to `<StarlightPage sidebar>`. A `<StarlightPage>` page can't join Starlight's autogenerated sidebar |
| The table of contents' entries and the headings' ids | **caracms** (`pageHeadings`, heading ids on every `h2`/`h3`) |
| `.md` twins, `/llms.txt`, `/llms-full.txt` | **The kit**, from the page JSON. `starlight-llms-txt` reads the `docs` collection, which is empty |
| Search | **Starlight's Pagefind**, over the built pages, production builds only |
| Asides, steps, tables, screenshots | **The kit's docs blocks**: caracms rich text is only paragraphs, lists, h2 and h3 |

*Rejected:* a content loader feeding caracms pages into Starlight's `docs` collection. It
gets search, sidebar and llms.txt for free, but loses editing on the page.

**The kit** is one folder, `src/starlight-kit/`, with no site names, colours or copy in it.
It ships inside the `caracms` package, at `node_modules/caracms/starlight-kit/`, and a site
copies it in (step 3): the site owns its copy. Each kit file opens with a comment saying
what it does and what it assumes; read those rather than guessing.

**Needs** a caracms that exports `pageHeadings` and `headingId` from `caracms/content` and
has `media({ altFrom })` (0.14.0 or later), and Starlight 0.42.

## 1. Setup, in order

Commands run from the site's root (`pnpm caracms …`, or `npx caracms …`).

1. **A Starlight site, its sample pages gone.** Start from Starlight (its template or by
   hand), delete everything in `src/content/docs/` and keep the folder with a `.gitkeep`.
   The site must be a git repo (`create astro` makes one unless you skip it; otherwise
   `git init`): step 2 commits the install. Keep `src/content.config.ts` as Starlight
   writes it, with a comment saying it's empty on purpose:

   ```ts
   // Empty on purpose: the pages are CaraCMS's, in content/pages.
   import { defineCollection } from 'astro:content';
   import { docsLoader } from '@astrojs/starlight/loaders';
   import { docsSchema } from '@astrojs/starlight/schema';

   export const collections = {
   	docs: defineCollection({ loader: docsLoader(), schema: docsSchema() }),
   };
   ```

   Starlight needs the collection defined to start. Its builds warn about it, and these
   are accepted (they can't be silenced without a real entry, and a real entry gets a
   Starlight route):
   - `[starlight-docs-loader] No files found matching … in directory "src/content/docs"`
   - `[content] The collection "docs" does not exist or is empty` (and the same for `"i18n"`)

2. **Install caracms and commit the install**, then run `init` with the mode. The install
   is `npm install caracms --save-exact` (`pnpm add --save-exact caracms`), committed
   before `init` (README → *Start*; `init --write` refuses over uncommitted changes).
   `caracms-hosting` has the cloud's order and the key:

   ```sh
   pnpm caracms init --cloud            # the dry run: read it
   pnpm caracms init --cloud --write
   pnpm install                         # it adds @astrojs/node
   ```

   `init` ends by pointing at the caracms-adopt skill. Ignore that on a Starlight site:
   there are no existing pages to bring in, so go straight to step 3.

   `--cloud` is the example; `--self-hosted` is the other mode. **Keep the `services`
   value `init` wrote** in step 4's config. A self-hosted site needs no key for dev or
   build; its built server's `/admin` answers 503 until its env is set, which is expected.

   `init` adds the Node adapter, turns off the dev toolbar, and puts `caracms(site)`
   **first in `integrations`, before `starlight(…)`**. Keep that order. It also writes
   the catch-all `src/pages/[...path].astro` (keep it as written), `src/pages/health.ts`
   (it stays), a starting page component and text block (replaced in
   step 4), and `allowImportingTsExtensions` in `tsconfig.json` (the kit's imports end in
   `.ts`).

3. **Copy `node_modules/caracms/starlight-kit/src/starlight-kit/` to `src/starlight-kit/`,
   at exactly that path.** The blocks name their components by path from the site's root
   (`'src/starlight-kit/blocks/Text.astro'`), so the folder can't move without editing them.
   Copy the kit's tests beside it: `node_modules/caracms/starlight-kit/test/` to `test/`
   (`test/kit/`, and `read.test.ts`, `write.test.ts` and `site.ts` in `test/markdown/`).
   They import the site's `caracms.config.ts` from step 4, and run through `tsx` (step 8
   has the script and why plain Node won't run them). The package's own
   `starlight-kit/caracms.config.ts` is the small config those tests ran against there; the
   site's own replaces it, so don't copy it.

   ```sh
   cp -R node_modules/caracms/starlight-kit/src/starlight-kit src/starlight-kit
   mkdir -p test && cp -R node_modules/caracms/starlight-kit/test/. test/
   ```

4. **Point caracms at the kit** in `caracms.config.ts`, and delete
   `src/components/caracms/Page.astro` and `TextBlock.astro`, then the empty
   `src/components/caracms/` folder (and `src/components/` too, if that leaves it empty):

   ```ts
   import { defineSite } from 'caracms/config';
   import { docsBlocks } from './src/starlight-kit/blocks/index.ts';

   export default defineSite({
   	services: 'cloud', // whatever init wrote
   	collections: {
   		pages: { kind: 'sections', folder: 'content/pages', urlBase: '/', nested: true },
   	},
   	blocks: docsBlocks,
   	textStyles: {},
   	page: 'src/starlight-kit/DocsPage.astro',
   });
   ```

   The kit's `text` block (field `body`) replaces `init`'s (field `text`). Then
   `pnpm caracms schemas` so the editor's schemas match. Don't add `settings.fields`:
   Site Settings' `brand` colours the editor only, never the public site.

5. **Add the kit's integration and the two overrides** in `astro.config.mjs`:

   ```js
   import { starlightKit } from './src/starlight-kit/integration.ts';
   // …
   integrations: [
   	caracms(site),
   	starlightKit(),
   	starlight({
   		title: '…',
   		components: {
   			Search: './src/starlight-kit/Search.astro',
   			ThemeSelect: './src/starlight-kit/ThemeSelect.astro',
   		},
   	}),
   ],
   ```

   `starlightKit({ groupLabels: { 'how-tos': 'How-to guides' } })` labels a sidebar group
   that is a folder with no page of its own, keyed by the folder's path; without it the
   group is labelled the way the editor labels the folder.

   **Remove the Starlight template's own `sidebar`** from `starlight({ … })` (the kit passes
   its own to `<StarlightPage>`, and the template's points at its deleted sample pages) **and its
   sample `social` link**. The site's look (logo, accent colour, fonts) goes in
   `starlight({ … })` and a `customCss` file outside the kit.

6. **Home is `content/pages/index.json`**: a normal docs page with a `title` and an
   `seo.description`. `llms.txt` takes its H1 and summary from them, so the kit holds no
   site name. The smallest one, in the stored shape:

   ```json
   {
     "$schema": "../../schemas/pages.schema.json",
     "title": "Product help",
     "seo": { "description": "How to use the product." },
     "blocks": [
       { "type": "text", "body": [{ "p": "Welcome. Pick a topic from the sidebar." }] }
     ]
   }
   ```

   The shapes are in `caracms-content` → *The file shapes*. After writing JSON by hand, run
   `pnpm caracms validate --fix`.

7. **Leave these alone:**
   - **No `src/pages/404.astro`.** Starlight's 404 builds as `/404.html`, and caracms sends
     visitors there for a missing or hidden page.
   - **No `site` in astro.config.** Starlight's bundled sitemap skips itself without it (it
     warns at build); caracms writes `/sitemap.xml` from `SITE_URL`. Set `site` and there
     are two.
   - **No `.md` or llms route files in `src/pages/`**: the integration injects them (see
     the traps).

8. **Check:** `pnpm caracms validate`, the kit's tests, `pnpm dev` and `/admin`, then
   `pnpm build`. Run the tests through `tsx`: add `tsx` as a dev dependency and this script
   to `package.json`:
   `"test": "tsx --test 'test/**/*.test.ts'"`.
   pnpm may report esbuild's build script as ignored (`ERR_PNPM_IGNORED_BUILDS`) when you
   add `tsx`: tsx works without it, or run `pnpm approve-builds`.
   Node's own `--experimental-strip-types` fails here with
   `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`: caracms ships `.ts` source, and Node won't
   strip types under `node_modules` (only a `link:` install escapes that).
   On Astro 7, `pnpm dev` runs in the background: stop it with `pnpm astro dev stop`.
   The build's `Some chunks are larger than 500 kB` warning is accepted too, along with the
   step 1 ones.
   A cloud site's build needs `CARACMS_CLOUD_KEY` (the traps); a self-hosted one doesn't.

## 2. The page component

`src/starlight-kit/DocsPage.astro`, the `page` in the config. It runs for the public site
and the editor's preview alike:

```astro
---
import StarlightPage from '@astrojs/starlight/components/StarlightPage.astro';
import Blocks from 'caracms/components/Blocks.astro';
import { pageHeadings } from 'caracms/content';
import type { PageProps } from 'caracms/document';
import { site } from 'virtual:caracms/config';
import { sidebarFrom } from './sidebar.ts';

type Props = PageProps;
const { document, collection, preview = false, listPage, read } = Astro.props;
const title = 'title' in document && typeof document.title === 'string' ? document.title : '';
const description = (document as { seo?: { description?: string } }).seo?.description || undefined;
const sidebar = await sidebarFrom(read);
const headings = await pageHeadings(site, document, { collection, read });
---
<StarlightPage frontmatter={{ title, description }} sidebar={sidebar} headings={headings}>
	<Blocks document={document} collection={collection} preview={preview} listPage={listPage} />
</StarlightPage>
```

- **Frontmatter:** the page's title is `frontmatter.title` (the H1 and `<title>`);
  `seo.description` is `frontmatter.description` (`<meta name="description">`).
  `seo.title` and the share image aren't used: Starlight writes the head.
- **Pass the render's own `read`** to the sidebar and the headings, so the preview shows
  drafts' titles and order.
- **Prev and next** come free: Starlight works them out from the sidebar.
- **`<html data-preview>` can't be set**: `<StarlightPage>` writes `<html>`. A site script
  that needs to know it's in the preview reads the frame's location instead.

## 3. The kit, file by file

| File | What it does |
|---|---|
| `DocsPage.astro` | The page component (section 2) |
| `sidebar.ts` | `sidebarFrom(read: DocumentReader): Promise<SidebarItem[]>`: the page tree as Starlight's user-config sidebar (`{ label, link }`, `{ label, items }`). Also `sidebarPages(read)`: the public pages in sidebar order |
| `blocks/` | The five docs blocks: a `.ts` schema and an `.astro` component each; `index.ts` exports `docsBlocks` (section 5) |
| `markdown/` | The Markdown writer and reader (`markdown/index.ts` is its seam), and `heading-id.ts`, which re-exports caracms's `headingId` |
| `writer.ts` | Re-exports `pageToMarkdown` for the routes |
| `llms.ts` | Which pages have a `.md` twin, and the text of `/llms.txt` and `/llms-full.txt` |
| `routes/` | `markdown.ts` (`/<address>.md`), `llms.txt.ts`, `llms-full.txt.ts`: prerendered |
| `integration.ts` | `starlightKit()`: injects the three routes |
| `Search.astro`, `ThemeSelect.astro` | Starlight's own, plus the preview fixes (section 6) |

**The contracts** (`markdown/index.ts`, `sidebar.ts`):

- `sidebarFrom(read)`: order is `read.documents('pages')`'s, which is the tree in Site
  Settings' `pageOrder` (the editor's Arrange pages screen; reordering there reorders the
  sidebar on the next build). A page with pages under it is a group labelled with its
  title, **its own page the group's first link**. A page without is a link. A folder with
  no page (the arrange screen can make one) is a group labelled like the editor labels it.
  Home (`index`) is left out (the site title links to it), and so are hidden pages and
  everything under one.
- `pageToMarkdown(entry: ReadEntry, options?): string`: one page as Markdown. `# Title`,
  then the blocks in order: text as paragraphs, `##`/`###` and lists; an aside as a
  blockquote opening `**Note:**`, `**Tip:**`, `**Caution:**` or `**Danger:**`; steps as a
  numbered list from `start`; a table as GFM (a list in a cell flattened to `<br>` lines,
  reported through `options.report`); a screenshot with a picture as `![alt](url)` with its
  caption in italics on the next line; an empty screenshot left out.
- `markdownToPage(md: string, options?): { title, description, blocks, report }`: the
  inverse, an importer's core. `# H1` is the title, the first paragraph after it the
  description (and it stays in the body). Every conversion that changes the text's shape
  is in `report`; nothing unknown is dropped silently. `options.dropLists` drops a `##`
  heading with one of those texts and the list after it (a hand-kept table of contents the
  sidebar replaces). Link rewriting and `pageOrder` belong to the import script around it
  (`mapStoredLinks`, `storedLinks` help).
- **Round trip:** `markdownToPage(pageToMarkdown(page))` gives the same blocks, except that
  empty screenshots are gone and a list in a table cell comes back as lines. The tests
  check it.
- `.md` twins: every public page at its address plus `.md`, Home at `/index.md`.
  `/llms.txt`: Home's title and description, then Home and top-level pages without
  children, then one `##` per sidebar group. `/llms-full.txt`: every page's Markdown, Home
  first, then sidebar order. Hidden pages are in none of them; their `.md` answers 404.

An importer for existing Markdown writes the page JSON itself, in the editor's layout
(`$schema` first, an empty screenshot without `image` or `caption`), not through
`caracms/serialize`'s `serializeDocument`, which drops `$schema`. Such a script, around
`markdownToPage`, must:

- map each source file to its page path under `content/pages/` (its folder becomes the
  page's parent; strip any number prefixes the source uses for ordering);
- rewrite links between source files to the pages' addresses (`mapStoredLinks`,
  `storedLinks`), and keep a link it can't resolve as it was, reporting it;
- write Site Settings' `pageOrder` in the source's order, so the sidebar keeps it;
- drop the source's hand-kept tables of contents (`options.dropLists`), since the sidebar
  replaces them;
- print every `report` entry, page by page, so a person can check each changed shape;
- be safe to run again: it overwrites the pages it writes and touches nothing else.

## 4. Heading ids

caracms gives every rendered `h2`/`h3` an `id`, on every site. One rule, three readers:
the rendered ids, the TOC (`pageHeadings`) and a Markdown writer's anchors all use
`headingId`.

- **The rule:** GitHub's slug of the heading's plain text (lower case, spaces to `-`,
  punctuation dropped; a line break reads as a space), made unique on the page with `-1`,
  `-2` in page order, counted across every block.
- **Page order is the document's**: blocks in order (a shared block where it's placed),
  each block's fields in schema order, list items in order. Only a block's own fields
  count: a page field, Site Settings and a slot's block get no ids. A heading with nothing
  to slug gets no id. Ids are render-only; the stored JSON never holds them.
- **From `caracms/content`:** `headingId(text, seen: HeadingSeen): string` (start each page
  with `new Map()`), `headingText`, `pageHeadings(site, document, { collection, read })`
  → `{ depth: 2 | 3, slug, text }[]`, which is `<StarlightPage headings>`'s shape.
- Never write a second slug function. The kit's `markdown/heading-id.ts` re-exports
  caracms's and adds `headingIds(texts)` for a whole page's headings.

## 5. The docs blocks

The keys are stored in content (`"type": "aside"`): never rename one.

| Block | Fields | Drawn with |
|---|---|---|
| `text` | `body`: rich text, h2/h3, links | `<RichText>`; its headings are the TOC |
| `aside` | `kind`: select note, tip, caution, danger (default note); `body`: rich text, no headings | Starlight's `<Aside>` |
| `steps` | `steps`: list of rich text, no headings; `start`: number, min 1 | Starlight's `<Steps>` around `<ol start>` |
| `table` | `header`: list of rich text; `rows`: list of `{ cells: list of rich text }` | a table that scrolls sideways on a phone |
| `screenshot` | `image`: `media({ only: 'image', altFrom: 'capture' })`; `capture`: text, "What to capture"; `caption`: text | `<Media>` in a `<figure>` |

- **A table row is `{ cells }`** because caracms refuses a bare `list(list(…))`. The header
  is its own field so an editor can't lose it by reordering rows.
- **Steps carry on their number.** When a screenshot or an aside interrupts a numbered
  list, the second steps block sets `start` ("First step's number" in the editor; stored
  only when above 1). Starlight's `<Steps>` numbers from the list's `start`, and the
  writer and reader keep it.
- **A screenshot's alt starts as "What to capture".** `altFrom: 'capture'` fills a picture's
  alt from the `capture` field when the picture is placed (picked or uploaded) and has no
  library alt; never later. The component also falls back to `capture` when the alt is
  empty, on the page and in the `.md`, for pictures placed before the option.
- **An empty screenshot draws nothing for visitors**, and in the preview a
  "Screenshot to add: …" placeholder with the capture text and the image's empty slot to
  upload into. An image value without a non-empty `key` is empty: no `<img>`, no request.
- caracms's `<Text>` renders a `<p>` by default; inside a `<p>` (the placeholder's label)
  or a caption, pass `as="span"`.

## 6. The editor's preview: the morph undoes Starlight's scripts

After an edit, the preview **morphs `<body>` back to the server's render** (`<html>` and
`<head>` stay; `caracms-blocks` → *Scripts and the live preview*). Any Starlight component
whose script sets state once, on load, has that state reset on the same elements, and the
script never runs again. **Fix each by overriding the component to redo it on
`caracms:rendered`**, the event the preview fires after each morph (never on the public
site):

- **Search** (`Search.astro`): renders Starlight's own `Search`, then on `caracms:rendered`
  re-enables `site-search button[data-open-modal]` (it's rendered `disabled`), shows the
  shortcut badge again, and on a Mac sets it back to "⌘ K" with
  `aria-keyshortcuts="Meta+K"`. The click handlers survive: same element.
- **ThemeSelect** (`ThemeSelect.astro`): renders Starlight's own, then on
  `caracms:rendered` calls `StarlightThemeProvider.updatePickers(<choice>)` with the
  choice read from `localStorage['starlight-theme']` ('' or missing is `'auto'`). Not the
  no-argument call: that uses the theme stored at page load, stale once the editor has
  switched it.
- The sidebar's `<details>` and the mobile menu were checked and are fine. After a
  Starlight upgrade, or when adding a Starlight component with a script, edit a page in
  `/admin` and check the search opens, the badge reads right and the theme select shows
  the theme in use.

**"Edited elsewhere: open Site Settings →"** shows on a click in Starlight's header in the
preview: the editor's rule for the frame a site draws itself. The click still goes through
(the search opens). Nothing in Starlight's header lives in Site Settings (the title is
astro.config's), so the pointer is misleading here; it isn't a bug in the site.

## 7. Other traps

- **Search only works in a production build.** In dev the dialog opens and says so.
  Check search on `pnpm build` and the built server. Starlight marks its content area
  `data-pagefind-body`, so Pagefind indexes the blocks and none of the editor's words.
  Pagefind's result URLs end in `/`; the built server answers both forms.
- **A cloud site's `pnpm build` refuses without `CARACMS_CLOUD_KEY`**: the build fetches
  the site's settings from the cloud. `pnpm dev` works without one. For local builds put a
  laptop key in `.env` (README → *Hosting → CaraCMS Cloud → Working locally*). Never
  print or commit it. A `services: 'self-hosted'` site has no such trap: dev and build
  need no key, and a built server's `/admin` answers 503 without its env.
- **`caracms start` on a laptop needs `CARACMS_CLIENT_IP_HEADER=socket`**; with no host
  detected it refuses to start:
  `pnpm build && HOST=127.0.0.1 PORT=<port> CARACMS_CLIENT_IP_HEADER=socket pnpm start`.
- **`caracms validate` rejects `src/pages/[...path].md.ts`** as a second route with
  parameters at the pages' address, then calls every page "served by the site's own code".
  It reads a rest parameter with a static suffix as a catch-all. That's why
  `integration.ts` injects the `.md` and llms routes instead of keeping them as files.
- **The `.md` and `.txt` content types come from the extension** on the built server
  (`text/markdown; charset=utf-8`, `text/plain; charset=utf-8`), not from the prerendered
  Response's header.
- **A linked caracms (`link:` to a cms checkout) brings its own astro.** Its code imports
  the cms workspace's astro while the site runs its own version. It works; if something
  astro-shaped breaks oddly, suspect this first. `file:` gives one astro but needs a
  reinstall per package change. A site on caracms from npm doesn't have this.
- **`astro check` crashes on Node 26** ("this.bridge.deleteEnv is not a function") when
  pnpm picks `@emnapi/runtime` 2.0.0-beta for `@astrojs/check`. Pin it in
  `pnpm-workspace.yaml`:

  ```yaml
  overrides:
    '@emnapi/runtime': 1.11.3
  ```

- **`CARACMS_ALLOW` takes a whole domain as `@example.com`**, not `*@example.com`.
- **`caracms audit` needs 0.20.1 or later here.** Before it, the audit's renders ran none of
  the site's middleware, so every page failed with `Astro.locals.t is not a function`
  (Starlight's middleware sets it) and nothing was checked. Its "Words no field holds" list
  still names Starlight's own fixed words on every page ("Skip to content", "Menu", "On this
  page", "Overview", "Next", "Previous", search's and the theme select's words): Starlight's
  to draw, not findings to fix. The rest are real: the sidebar's group labels (`groupLabels`
  in astro.config), and words the kit's components and docs blocks write in code.

## 8. What's generic and what's the site's

**Generic, in the kit:** everything in `src/starlight-kit/`. It assumes a nested `pages`
collection with `urlBase: '/'`, a Home page at `index`, and the five blocks as they're
stored. Its site name and summary come from Home's title and description.

**The site's own, outside the kit:**

- `starlight({ … })` in astro.config: title, logo, favicons, `customCss`, and the CSS
  file with the accent colour and fonts.
- `content/` (Home and the pages) and Site Settings' `pageOrder`.
- An import script, if the site starts from Markdown (section 3 says what it must do): it
  is tied to that source's folders, prefixes and hand-kept lists, so it belongs to the site.
- Its hosting config, the dev ports, `.env`.

**Not done yet**, so not in the kit: inline code and code blocks (caracms rich text has
neither), Starlight's `<Tabs>`, `<Card>` and `<FileTree>`, and copying this skill only into
Starlight sites (`init` copies it into every site; its description tells other sites to
skip it).
